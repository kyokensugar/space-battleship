# Space Battleship Game — 設計書 v1.0(MVP)

## 0. 要件の見直し(ご指摘の2点)

### 最大ターン数(R-10, R-12)
- 古典 Battleship には**存在しない**ルールです。全マスは100、艦は17マスなので、最長でも100手以内に必ず決着します(無限ループになりません)。
- **提案: 削除**。ターン数は「何手で勝ったか」の記録としてだけ表示します。

### HP 表示(R-09)
- 古典では「HP」という数値ではなく、**「残っている艦の一覧」**を表示します(旗艦 ○ / 戦艦 × 撃沈 …)。プレイヤーはこれを見て「まだ2マスの偵察艇が残っているな」と推理します。これは Battleship の推理要素の核なので、**HP数値ではなく残艦一覧に置き換える**ことを提案します。
- 内部的には「残りマス数」は勝敗判定に使うので、数値としては保持します(見せ方だけ変える)。

→ 承認いただければ要件定義書を v1.1 に更新します。

## 1. どんな技術を使うか

### 選択肢
| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | HTML + CSS + 素の JavaScript | 道具が最少。仕組みが見えやすい | 画面が複雑になると管理が大変。型チェックがなくバグに気づきにくい |
| B | **TypeScript + React + Vite** | Web 業界の標準構成。型でバグを早期発見。部品(コンポーネント)単位で画面を組める。公開が簡単 | 最初に覚える道具が少し多い |
| C | Python + Pygame | Python は読みやすい | ブラウザで公開しにくい(URLで遊ばせるのが難しい) |
| D | Unity / Godot(ゲームエンジン) | 本格的な演出が可能 | 今回の規模には過剰。学習コストが高く、開発プロセス理解という目的から逸れる |

### 推奨: B(TypeScript + React + Vite)
- 理由: 「URLを開けば遊べる」を最短で実現でき、テスト・CI・公開まで一貫して業界標準の流れを体験できる。
- 各道具の役割(たとえ):
  - **TypeScript** = 文法チェック付きの JavaScript。「数字を入れるべき所に文字を入れた」等を実行前に教えてくれる。
  - **React** = 画面を「部品」に分けて作る道具。グリッド、マス、艦一覧をそれぞれ部品にする。
  - **Vite** = 開発サーバー & ビルド(公開用ファイルへの変換)ツール。保存すると即ブラウザに反映。
  - **Vitest** = 自動テスト実行ツール(Vite と相性が良い)。

## 2. ゲームをどんな構造で作るか

### 設計方針: 「ゲームのルール」と「画面」を完全に分ける
```
src/
  game/            ← ゲームロジック(画面を一切知らない純粋な計算)
    types.ts       ← 座標・艦・盤面などの「型」の定義
    board.ts       ← 盤面の作成、艦の配置、配置が合法かの判定
    shoot.ts       ← 砲撃 → Hit / Miss / Sunk の判定
    rules.ts       ← 勝敗判定
    ai/
      easy.ts      ← Easy AI(未砲撃マスからランダム)
      (normal.ts, hard.ts は後で追加)
  ui/              ← 画面(React コンポーネント)
    App.tsx        ← 画面の切替(開始 → 配置 → 対戦 → 結果)
    Grid.tsx       ← 10×10 グリッド
    Cell.tsx       ← 1マス
    FleetStatus.tsx← 残艦一覧
    ...
  i18n/            ← (後で追加)言語辞書
```

### なぜ分けるのか
- ロジックが画面から独立していると、**画面なしでテストできる**(「(3,4)を撃ったらヒットになるか」をプログラムで検証)。
- 後で Normal/Hard AI を足すとき、`ai/` にファイルを1つ増やすだけで済む。
- UI を作り直しても、ルール部分は一切触らなくてよい。

### ゲームの状態(データ)の考え方
ゲームは「1つの状態オブジェクト」で表現し、操作のたびに新しい状態を作ります。
```
GameState {
  phase: "setup" | "battle" | "finished"
  player: { board, fleet, shotsReceived }
  ai:     { board, fleet, shotsReceived }
  currentTurn: "player" | "ai"
  turnCount: number
  winner?: "player" | "ai"
}
```
砲撃は `shoot(state, target) → 新しい state` という「関数」として実装します。入力と出力が明確なので、テストしやすく、バグの原因も追いやすいです。

### 画面遷移(MVP)
1. **開始画面**: 「ゲーム開始」ボタン(難易度は Easy 固定。選択UIは後で)
2. **配置画面**: 自分の艦を置く(クリックで置く/回転、ランダム配置ボタン)
3. **対戦画面**: 左=自分の宙域(AIの砲撃跡)、右=敵の宙域(自分の砲撃跡・クリックで砲撃)、下=両者の残艦一覧
4. **結果画面**: 勝敗、手数、敵配置の公開、「もう一度」

## 3. どのようにテストするか

### 3層のテスト
| 層 | 対象 | 方法 | 例 |
|---|---|---|---|
| ユニットテスト(自動) | `game/` のロジック | Vitest | 「盤外に艦を置いたらエラー」「17マス全部ヒットで勝ち」「Easy AI は同じマスを2度撃たない」 |
| コンポーネントテスト(自動・最小限) | 主要な画面部品 | Vitest + Testing Library | 「マスをクリックすると砲撃が実行される」 |
| 手動プレイテスト | ゲーム全体 | 実際に遊ぶ | 「最後まで遊べて勝敗が出る」 |

### 進め方
- ロジックは**テストを先に書いてから実装**する場面も作ります(TDD)。「ルールを先にテストとして書く = 要件を機械が読める形にする」という感覚を体験できます。
- 自動テストは GitHub 上で毎回自動実行(後述の CI)。

## 4. GitHub をどう使うか

### 基本の流れ(1機能ごとに繰り返す)
1. `main` ブランチ = 常に動く「正」のコード
2. 機能ごとに**ブランチ**を切る(例: `feature/board-placement`)
3. コードを書いて**コミット**(変更のスナップショットに説明を付けて保存)
4. **Pull Request(PR)**を作る = 「この変更を main に入れてよいか?」の提案
5. **CI(GitHub Actions)**が自動でテスト・型チェックを実行し、結果を PR に表示
6. あなたが PR の説明とテスト結果を見て**承認・マージ**
7. 不具合があれば **Issue** で記録 → 修正 PR

### 今回の役割分担
- 私: ブランチ作成・実装・テスト・PR 作成・PR 説明文(非エンジニア向けに「何を・なぜ」を書く)
- あなた: PR を読んで質問・承認・マージ。これが「レビュー」体験になります。

### 必要な準備
- GitHub に新しいリポジトリ(コードの置き場所)を1つ作る。例: `kyokensugar/space-battleship`
  - あなたが作成して私にアクセス権を付与する、または私が作成する(権限があれば)。

## 5. どうやってインターネット上に公開するか

### 選択肢
| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| A | **GitHub Pages** | 無料。GitHub だけで完結。main にマージすると自動公開できる | URL が `kyokensugar.github.io/space-battleship` 形式に固定 |
| B | Vercel / Netlify | 無料枠あり。PR ごとにプレビューURLが出る | 別サービスの登録が必要 |
| C | 自前サーバー(VPS等) | 自由度が高い | 有料・運用の手間。今回は過剰 |

### 推奨: A(GitHub Pages)
- このゲームは**サーバー不要**(すべてブラウザ内で完結)なので、静的ファイルを置くだけで公開できる。
- GitHub Actions で「main にマージ → ビルド → 公開」を自動化(これが CD = 継続的デリバリー)。

## 6. MVP の実装計画(PR 単位)
| # | PR | 内容 | 主なテスト |
|---|---|---|---|
| 1 | プロジェクト初期化 | Vite + React + TS + Vitest、CI 設定、README | CI が動くこと |
| 2 | 盤面と艦の配置ロジック | `types.ts` `board.ts` | 合法/非合法配置、ランダム配置 |
| 3 | 砲撃と勝敗ロジック | `shoot.ts` `rules.ts` | Hit/Miss/Sunk、全艦撃沈で勝利 |
| 4 | Easy AI | `ai/easy.ts` | 重複砲撃しない、必ず未砲撃マスを選ぶ |
| 5 | 画面: 配置 | `Grid` `Cell` 配置画面 | クリック配置、ランダム配置 |
| 6 | 画面: 対戦・結果 | 対戦画面、残艦一覧、結果画面 | 一連の操作 |
| 7 | GitHub Pages 公開 | デプロイ用 Actions | URL で遊べる |

各 PR は「動く小さな単位」で、マージのたびにゲームが少しずつ完成に近づきます。
